# album-studio — Plan v3.2 (2026-07-28, post-daemon-decision)

> **v3.2 supersedes v3.1 entirely.** Same critical re-think lineage (v2 → v3 →
> v3.1 → v3.2), but with the architectural spine settled: a local Servy
> daemon owns HTTP, SQLite, and the build-job queue. The static HTML is
> a thin viewer over that daemon. Penelope is a first-class client. CLI
> is the embeddability contract. Everything writes to one SQLite file
> via WAL.
>
> **What changed v3.1 → v3.2:** 8 new locked decisions (Q27–Q34). The
> plan gained 5 build days and ~2,200 LOC of code in exchange for a
> reliable, sturdy centerpoint that the rest of the system hangs off.
> No more JSON-bridge workarounds. No more CLI-only-as-truth
> pretending. One source of truth (SQLite), one bus (daemon), many
> clients (studio / Penelope / CLI).

### Decisions 27–34 (NEW in v3.2)

| # | Question | Decision |
|---|---|---|
| **Q27** | Album-session model | **`album_sessions` is a first-class table.** FK to `albums`. UUID for resume. Status ∈ `active` / `paused` / `done` / `archived`. All activity tables (`events`, `decisions`, `api_prompts`, `api_responses`, `pipeline_state`) gain a `session_id` FK. `albums.status` derived via trigger. UI: in-progress = badge + click-to-edit, done = no badge + click-to-play, reopen via `[reopen]` button on done cards. Multi-session per album supported. |
| **Q28** | mmx retry policy | **Never auto-retry.** Every failure surfaces immediately via `action_failed` event with the actual error. User clicks `[retry]` to re-invoke or `[skip]` to mark as failed-and-moved-on. |
| **Q29** | Daemon vs CLI | **Both.** A local Python daemon (`Servy_AlbumStudio` via Servy/NSSM) on `127.0.0.1:8765` serves as the HTTP API + SQLite writer + build-job queue owner + static file server. CLI (`python -m tools.album_studio invoke`) is the actual work executor (one mmx call per CLI run). Penelope (the agent) interacts via SQLite directly + HTTP for state queries. CLI does NOT auto-restart on failure (Q29a). **`README contract amended` — no longer "not a backend."** |
| **Q30** | Asset versioning + cleanup | **Versioned filenames** (`<slug>-cassette-v2.png`). Library always uses the highest version. `_OLD/` folder per media type holds superseded versions. `python -m tools.album_studio finalize <album>` runs **manually** when the album is done — moves all non-current versions to `_OLD/`, generates `_OLD/INDEX.md` audit trail. |
| **Q31** | Edit affordance | **Chat text input is the edit affordance.** Build skill parses → emits `edit_proposed` event with parse summary → user confirms (`y`) → build skill applies. Confirmation step is mandatory; no silent parse-and-apply. |
| **Q32** | Idle auto-pause + session cap | **`active → paused` after 12 hours of no activity** (no new events/decisions/api_prompts). Sweeper runs every 5 minutes in the daemon + nightly cron. Auto-pause emits `session_auto_paused` event with idle duration. **Max 3 active sessions** across all albums (mirrors Hermes desktop session limit). App-layer guard, NOT SQLite CHECK (cross-row constraints aren't reliable). |
| **Q33** | Chat input channel | **Hermes/Penelope is the chat input.** Studio HTML's chat box is a notepad-like input that POSTs to the daemon (`/api/sessions/<uuid>/events`). The daemon writes the user event; the message sits as "🤖 awaiting Penelope..." in the studio. When you chat with me (Penelope), I read the latest user events, respond, write `assistant` events. The studio's next poll picks them up. **Studio = viewer; Penelope = brain.** |
| **Q34** | Daemon scope | **Daemon serves everything on one port.** Static HTML/CSS/JS, audio files (range-requested), cover art, cassette stickers, AND the JSON API. Single origin = no CORS, no file:// issues, no port confusion. Reliability sidecars: `/api/health` with subsystem status, quota monitor (every 5 min), WAL checkpointer (every 15 min), OneDrive mirror watcher (every hour), log rotation (daily / 10MB), graceful shutdown on SIGTERM. Daemon is the operational spine. |
| **Q29a** | `invoke` contract | **1 mmx call per CLI process per event write.** A multi-mmx layer (e.g. L6 cover art = 3 candidates + 1 select + 1 embed) = 5 sequential `invoke` calls, tracked as ONE `build_job` with N child events. *Locked 2026-07-29 §4.A.* |
| **Q29b** | Invoke concurrency | **Max 1 invoke process at a time.** SQLite advisory lock (`BEGIN IMMEDIATE`) serializes mmx calls. b2/b3 (parallel + retry) conflict with Q28 (no auto-retry). *Locked 2026-07-29 §4.B.* |
| **Q29c** | Pipeline definition | **Declarative DAG.** `pipeline-deps.json` defines the 12-layer graph (each layer: `depends_on[]`, `approval_required`, `mmx_action`, `output_table`). CLI reads deps to know "L_i can run iff all L_j in depends_on are approved." No imperative per-layer scripts in v1. *Locked 2026-07-29 §4.C.* |

| **Q29d** | Daemon heartbeat (orphan recovery) | **SQLite-backed heartbeat.** Each `invoke` process writes `heartbeat_at` to its `build_job` row every 5s. Daemon on startup scans for `build_jobs.status='running' AND heartbeat_at < now - 30s` → marks as `orphaned` → emits `action_failed` event with reason. User clicks `[retry]` to re-invoke. *Locked 2026-07-29 §5.A. Daemon is the single source of truth for liveness.* |
| **Q29e** | Long-idle policy | **12h idle = auto-pause, no auto-archive.** User can keep a `paused` session for months. Manual `archive` and `finalize` only — explicit user actions. *Locked 2026-07-29 §5.B. UI: `paused` sessions show `[resume] [archive] [finalize]`. No tier escalations.* |
| **Q29f** | Single-active-session-per-album (ironclad) | **Three-layer defense.** (1) **SQLite partial UNIQUE index** `CREATE UNIQUE INDEX uniq_album_active ON album_sessions(album_id) WHERE status='active'` — DB rejects duplicates. (2) **App-layer guard** in `create_session` — `SELECT 1 FROM album_sessions WHERE album_id=? AND status='active'` first, return 409 if exists. (3) **Client-side button debounce** — studio's `[new session]` button: disabled on click, optimistic-nav to new state, re-enabled only on: API success (navigate), API 409 (show existing session with toast "session already active"), or 60s timeout. *Locked 2026-07-29 §5.C.* |
| **Q35** | Chat surface scope | **Chat appears in TWO places only, both during the active creation phase.** (1) Intake form (`/intake.html`) — chat panel for asking clarifying questions WHILE filling out the questionnaire. (2) Studio shell (`/studio.html?session=<uuid>`) — chat panel for the live session. **Gone after album is `archived` or `finalized` (done).** Library + albums listing pages have NO chat — just static records. *Locked 2026-07-29 §6.A.* |
| **Q36** | Buttons + chat hybrid | **Both work, both required.** Per-layer buttons (`[regenerate]`/`[approve]`/etc) are primary for layer actions — they write the decision event directly. Chat input is for everything else: meta-questions ("what should I do next?"), inline edits ("change this lyric to …"), non-layer commentary. Chat parser emits either `chat_message` (pure commentary) or `action_requested` (layer action). Parse confidence: ≥0.95 = execute, <0.95 = confirm with `[do this]` button. *Locked 2026-07-29 §6.B.* |
| **Q37** | Real-time delivery | **Option 3 — WebSocket.** Bi-directional `/ws/sessions/<uuid>` endpoint on the daemon. ASGI bridge (FastAPI or Quart) replaces WSGI. Effort: ~17h. **Graceful fallback: if WebSocket proves infeasible (Servy/NSSM doesn't survive the upgrade, or reconnect logic is too brittle), downgrade to Option 2 (SSE) — still streams events server-to-client, falls back to POST for chat input.** Decision point: end of Day 3 — if the WS endpoint isn't pinging reliably by EOD, switch to SSE. Day 4+ assumes WS works (build kit tests WS). *Locked 2026-07-29 §6.C.* |

### Why this is the right shape

**Single source of truth:** SQLite (with WAL). Daemon, CLI, Penelope, and
(studio-via-daemon) all read/write the same file. No sync needed.

**Single bus:** The HTTP daemon. Every client talks HTTP to it.
- The browser (studio) reads + writes via fetch.
- Penelope (the agent) reads SQLite directly for speed; writes via HTTP
  when the studio needs to see the change.
- CLI writes to SQLite directly; the daemon sees the side effects.

**Single lock:** The SQLite advisory lock (`build-skill.lock`). The CLI
takes it before doing work. The daemon never holds it; it spawns
subprocesses that take it.

**No IPC mess:** Daemon and CLI don't talk to each other. They both
talk to SQLite. SQLite is the protocol.

## 3. The contract (the README gets amended)

### v3.1 said

> *"Not a backend / API. Both pages are pure static HTML + inline CSS/JS."*

### v3.2 says

> **Local-first, daemon-backed, single-user, single-machine.**
>
> The studio pages are static HTML + CSS + JS served by a small local
> Python daemon (`Servy_AlbumStudio`, port 8765). The daemon is a write-log
> + HTTP API — NOT a backend with business logic. The build skill does all
> generation work via one-shot CLI invocations; the daemon is just the bus
> between studio, the agent, and SQLite.
>
> Single user, single machine, port-bound to `127.0.0.1`. No auth (local-only).
> SQLite (with WAL) is the system of record. Graceful degradation: if the
> daemon is down, the studio shows a banner and read-only mode still works
> (library view + static HTML served via Python's stdlib in a fallback).
>
> The CLI (`python -m tools.album_studio`) is the embeddability contract.
> External agents (Hermes, custom scripts, future automations) drive the
> system through the CLI; they do not render the web UI.

### Phase 0.U — Pre-build: UX bulletproofing patterns (BEFORE Day 1, cross-cutting)
- **One-state-screen rule:** every interactive surface has exactly one "current state" badge (e.g. "creating…" / "active" / "paused"). The next state is unreachable until the current one resolves or the user explicitly cancels.
- **Button debounce table** (transcribed from §5.C, applies to all `[create]` / `[submit]` / `[approve]` / `[regenerate]` buttons):
  - On click: button → `disabled` + spinner + label change (e.g. "Creating…")
  - On 2xx: navigate to next screen OR re-render current with success state
  - On 4xx: show toast with specifics ("Album already exists" / "session already active") + return to pre-click state with button re-enabled
  - On 5xx / network: show "Couldn't reach daemon (is it running?)" + retry button + return to pre-click state
  - On 60s timeout: re-enable regardless + show "request timed out — try again"
- **Idempotent navigation:** POST is idempotent within the 60s window. Backend uses `Idempotency-Key` (UUID per click) to dedupe. Duplicates return the original 2xx response, not a new session.
- **Resilience over perfection:** prefer "looks slightly broken for 30s" over "double-submitted created two sessions." Optimistic UI is OUT for v1; every action waits for daemon confirmation.
- **File: `site/css/ux-states.css`** — single source of truth for `disabled`, `loading`, `success`, `error`, `timeout` state visuals
- **File: `site/js/debounce.js`** — tiny helper: `debounceButton(el, fn, {timeout: 60000, idempotency: true})` — applied to every action button via a data attribute
