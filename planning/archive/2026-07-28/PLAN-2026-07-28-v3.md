# sonic-studio — Plan v3.0 (2026-07-28, critical re-think)

> **v3 supersedes v2 entirely.** This is a critical re-think after auditing
> the README, DESIGN.md, intake.html, dashboard.html, schema.json, CONCEPT-BRIEF
> TEMPLATE, the `full-album-release-package` skill (which has its own
> "When the user asks for a UI..." recipe), and the existing prototype
> templates. v2 made assumptions that contradicted the existing contract.
> v3 honours the contract.

---

## 0. The fundamental correction

v2 violated the README. The README is explicit:

> "**Not a backend / API.** Both pages are pure static HTML + inline CSS/JS."
> "**Not a music streaming service.** The agent delivers MP3s; the user
> uploads to distributors."
> "The site is **NOT a replacement for the agent** — it's a surface that
> makes the skill workflow visible and inspectable. The agent still does
> all the heavy lifting."

v2 designed a FastAPI daemon with 25 endpoints, SQLite catalog with 9 tables,
206 Partial Content audio streaming, drag-drop cassette deck UI, Servy
service `Servy_AlbumStudio`, CLI binary, 7-day phased build, 7,700 lines of
new code. **All of that violates the contract.** It's a different product.

The `full-album-release-package` skill has a recipe called "When the user
asks for a UI / dashboard / website over this pipeline" — it explicitly says:

> **DON'T redesign a pipeline when the user asks for a UI.**
> **DON'T list "future expansion" capabilities that already exist.**
> **DON'T propose a v0/v1/v2 progression that includes re-implementing solved layers.**
> **The website is a control panel + display surface, not a pipeline.**

v3 follows that recipe. The pipeline is solved. The new things are
**three small, surgical additions** to the existing static surface.

```
│          │                   │   state.json     │                └────────────┘

```

**Five pain points in this flow:**

1. **No overview.** User opens dashboard.html and sees one album. If they
   have 3 albums in flight, they have to remember the slug and pass it via
   `?album=<slug>` URL param (which isn't even implemented yet — dashboard
   defaults to `.meta/state.json`).
2. **No "where do I go next" hub.** The README admits this: dashboard
   renders empty state with "CTA to intake.html". But there's no single
   front page.
3. **The intake form is one-shot.** Once you click "Generate CONCEPT-BRIEF"
   and the JSON downloads, the form clears localStorage. To revise a
   brief you have to start over (no resume).
4. **No way to see the brief from the dashboard side.** After approving,
   the brief lives in `concept-briefs/<slug>/CONCEPT-BRIEF.md` but the
   dashboard doesn't link to it.
5. **No library browse.** If a user has Maren Sol completed + a new album
   in flight, the dashboard can't show both.

## 6. The 3 unsolved implementation details

These are real questions I need you to answer or decide on. I've put
my recommendations but flag each as a real question.

### 6.1 How does studio.html know which albums exist?

**The blocker.** Browser JS can't `fetch('file:///music/')` — that
returns a directory listing error (Chromium blocks it; Firefox returns
text/plain). Three solutions:

| Option | Pros | Cons |
|---|---|---|
| **A. Hand-maintained `.meta/albums.json`** | Simple. No backend. Works everywhere. | User has to update it manually when adding albums. |
| **B. Tiny Python helper** `python -m http.server 8000` that runs `python -m sonic_studio.scan --write .meta/albums.json` | Already need http.server to serve the pages anyway (file:// blocks localStorage in some configs). One tool, one job. | Adds one command. |
| **C. Native FS Access API** | No helper. Browser reads the directory. | Chromium-only. Firefox/Safari don't support it. 2026 is too early for cross-browser. |

**My pick:** **A** (hand-maintained `.meta/albums.json`).
The agent writes it whenever it creates a new album folder. The studio
page reads it on load. This honors the README's "no backend" rule.

**Question for you:** do you want me to add `albums.json` to the agent's
brief-write step (auto-update on brief approve), or maintain it by hand?

### 6.2 How does intake.html pre-fill from an existing brief?

The intake form is one-shot today (localStorage autosaves within a session,
but clears on export). For "edit existing" we need to:
1. Read `concept-briefs/<slug>/CONCEPT-BRIEF.md` (or
   `intake-data/<slug>.json` if available — that has the structured form)
2. Parse it back into form field values
3. Hydrate localStorage with the parsed values
4. Switch the form to "edit" mode (different CTA: "Save updated brief" instead
   of "Generate CONCEPT-BRIEF")

**The structured brief is the right source** (`intake-data/<slug>.json`)
because it's machine-readable. The CONCEPT-BRIEF.md is human-readable.

**My pick:** Read `intake-data/<slug>.json` if it exists; fall back to
parsing the CONCEPT-BRIEF.md if not.

**Question for you:** when a user edits an existing brief, do we want the
updated JSON to (a) overwrite the old `intake-data/<slug>.json` (lossy,
loses original) or (b) write `intake-data/<slug>-v2.json` and the agent
handles the rename? My pick: **(b)** — versioned JSONs, agent decides.

### 6.3 What goes in `.meta/albums.json`?

The library manifest. Smallest useful schema:

```json
{
  "version": "1.0",
  "updatedAt": "2026-07-28T18:01:00Z",
  "albums": [
    {
      "slug": "maren-sol-half-light-hours",
      "artist": "Maren Sol",
      "title": "Half-Light Hours",
      "status": "complete",
      "tracks": 10,
      "runtimeMinutes": 37,
      "year": 2026,
      "coverArt": "~/OneDrive/Hermes/albums/Half-Light-Hours/cover-art/album-cover-front-square.jpg",
      "conceptBriefPath": "concept-briefs/maren-sol-half-light-hours/CONCEPT-BRIEF.md",
      "stateJsonPath": "music/maren-sol-half-light-hours/state.json",
      "source": "imported",
      "importedAt": "2026-07-28T18:00:00Z"
    }
  ]
}
```

**My pick:** this exact shape. Six fields are visible in the UI
(artist, title, status, tracks, runtime, year); the rest is wiring.

**Question for you:** should the manifest also store the cover art path
as a relative path (so the project is portable) or absolute (so it works
on any machine)? My pick: **relative** with a fallback to the canonical
OneDrive path.

## 7. What v3 deliberately does NOT do

These are features v2 promised that v3 drops. Each one has a reason.

| Feature | Why v3 drops it |
|---|---|
| **Python daemon** | README: "Not a backend / API." |
| **SQLite catalog** | Premature. One album exists. Adding a DB layer before the user has 3+ albums is over-engineering. The manifest file (`.meta/albums.json`) is sufficient for v3. |
| **Audio streaming endpoint** | README: "Not a music streaming service." The agent delivers MP3s; user opens them in their music player of choice (VLC, foobar2000, etc.). |
| **Cassette-deck player UI** | Same. The web is a control panel, not a player. If you want a player, that's a separate project (and a daemon to back it). |
| **Drag-and-drop library** | Nice but unnecessary. Click-to-open works. Drag-drop is a one-time "wow" that doesn't pay back the complexity. |
| **Servy service** | README: static HTML. The pages work via `file://` or any static server. No service needed. |
| **CLI binary** | Not in scope. README doesn't mention it. |
| **Per-album sticker upload** | Useful but not in v3. v3 = ship the library shell. Stickers = v4. |
| **Chat-tuning panel in UI** | The chat IS Penelope. Adding a chat panel inside the dashboard is a different product. |
| **MiniMax generation buttons in dashboard** | The dashboard reads state.json. The build skill writes it. Adding buttons muddies the contract. Build skill calls `mmx_image_generate` etc. |
