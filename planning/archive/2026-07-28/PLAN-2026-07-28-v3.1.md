## 1. The 22 locked decisions (Q&A record)

These were asked one by one over the planning conversation. Each is locked. No re-litigation without user signal.

### Q0. Daemon vs static shell + CLI tool
**Locked: Static shell + CLI tool.** No Python daemon. No Windows service. The static shell is HTML/CSS/JS; the build skill is a CLI invoked per action. The studio URL is `http://localhost:8000/site/studio.html`.

**Why not daemon:** the user has 1 album, 1 artist, 1 operator. A daemon solves problems the user doesn't have. README also explicitly forbids it.

### Q1. Where do MP3s live
**Locked: OneDrive canonical, project copy on build.** `~/OneDrive/Hermes/albums/<Slug>/music/NN-slug.mp3` is the canonical source. The project gets a copy at `music/<Slug>/music/NN-slug.mp3` when the album is built (via build skill). The player reads from the project folder so MP3s are same-origin with the HTML.

### Q2. Static server auto-start
**Locked: Auto-start via build skill entrypoint.** Every time the build skill runs, it first checks port 8000 (`socket.connect_ex`). If free, spawns `python -m http.server 8000` as a child process (CREATE_NO_WINDOW, detached). If busy, assumes already running. The studio URL is bookmarkable.

### Q3. Drag-drop library affordance
**Locked: Skip.** Click-to-open only. Drag-drop is "wow" affordance without payback on a single-user local app.

### Q4. Per-album cassette sticker
**Locked: Auto-generated by the build skill.** When cover art ships (Layer 4), the build skill auto-generates a `<slug>-cassette.png` (600×340 horizontal cassette label image) using `mmx_image_generate`. Same color palette, same artist brief. The cassette card on the library uses the generated image. **No manual upload affordance.**

### Q5. Album metadata (the Maren Sol schema)
**Locked: Keep everything from Maren Sol.** ID3 tags, ISRC codes, LRC lyrics, cover art, press package, merch, social posts — all are important. The dashboard's per-album view surfaces the existing `tag-manifest.json` as a read-only metadata table. No edit affordance, no schema rewrite, no cleanup. Future metadata revisions are by chat.

### Q6. Album manifest scope
**Locked: `~/OneDrive/Hermes/albums/` is the canonical source.** Media MAY exist elsewhere (duplicated for stories, one-off renders, etc.) but those duplicates are derived, not canonical. The studio reads ONLY from the albums folder. Adhoc MP3s in `~/Music/`, `~/Downloads/`, etc. are not scanned. **The studio's truth is the albums folder.**

### Q7. Library card shape
**Locked: A — mini horizontal cassette (400×260).** Matches the full player aesthetic. The cassette metaphor is the visual anchor.

### Q8. Edit-existing brief affordance
**Locked: A — `intake.html?edit=<slug>` pre-fills the form.** Same form surface, populated fields, "Save updated brief" CTA instead of "Generate CONCEPT-BRIEF." No separate editor screen.

### Q9. Edit-existing JSON lifecycle
**Locked: B — versioned JSON (`<slug>-v2.json`).** Original stays as `<slug>-v1.json` after v2 ships. The build skill handles the rename. **Paper trail without a directory per album.**

### Q10. Chat panel inside studio.html
**Locked: B — yes, chat panel inside studio.html.** Full UI independence from Hermes. The chat panel is the studio's own chat surface, talking to the build skill directly via `.meta/events.jsonl`. **Not** an iframe of Hermes. **Not** the Hermes chat. The studio is its own product.

### Q11. Pipeline buttons per layer
**Locked: B — yes, buttons per layer.** `[regenerate]` / `[approve]` / `[reject]` / `[skip]` per layer. Buttons invoke the build skill as a per-action CLI (`build-skill invoke --layer N --album <slug> --action regenerate`). ~1.5s startup per click. No long-running serve.

### Q12. 3-option picker modal at studio start
**Locked: A — no modal.** Single `[+ Start a new album]` button → `intake.html`. Library cards also have a "Fork from this album" link. One CTA, one path.

### Q13. Mobile-aware layout
**Locked: Partially responsive from day 1.** Layout uses CSS grid + flex, no fixed widths, no JS-only positioning. Desktop is the primary form factor. Mobile is graceful (single column, no drag-drop, no fancy interactions). **Future-proofed, not polished.**

### Q14. Notification system
**Locked: A — tab title flash + chime + visible chat feed.** The chat panel surfaces what was triggered, what's running, what failed. **The user wants traceability, errors, and progress visible — because the build skill will fail and ask questions.** Browser-native (`document.title` + `<audio>` chime). No push notifications, no service worker, no daemon.

### Q15. Build scope
**Locked: ALL features in v3.1.** Ship over the week. Static shell + library + cassette player + auto-start server + build-skill CLI + cassette sticker generation + chat panel + pipeline buttons + mobile-aware layout + OneDrive mirror. **Not shipped today. Planned now, built incrementally next week.**

### Q16. OneDrive mirror
**Locked: A — mirror everything.** Every write triggers a OneDrive mirror with md5 verification. Matches the user's existing rule.

### Q17. Chat panel persistence
**Locked: A — live-tail only.** Chat session is the current album session. When the user switches albums, the chat resets to the new album's live-tail. Old sessions are visible in the album's history view (read-only `.meta/events-archive.jsonl`).

### Q18. Action sequencing model
**Locked: A — stop & confirm.** Each layer runs to completion (or fail), then blocks for user decision. No auto-advance. **No parallel runs because of rate limits.** The user wants to see what was triggered, give feedback mid-flight via chat, then approve before the next layer.

### Q19. Cassette sticker regeneration
**Locked: A — one-shot.** Cassette sticker is part of core album media. Generated ONCE when cover art ships. Never auto-regenerated. Only regenerated by explicit user ask.

### Q20. Chat feed shape + concurrency
**Locked: A — single scrolling feed.** Color-coded by event type (info/warn/error/question). Newest at bottom. **If one action is running, the user CANNOT start another — UI locks + build skill refuses via mutex.**

### Q21. Build skill question UX
**Locked: B — inline chat question.** The build skill surfaces questions as styled messages in the chat feed. User replies in the chat panel. **Chat is the primary interface for out-of-band questions.**

### Q22. Build skill invocation model
**Locked: A — per-action CLI invocation.** Each button click spawns a Python process (`build-skill invoke --layer N --album <slug> --action regenerate`). ~1.5s startup per click. **No long-running serve. Simpler. Simpler is what the user asked for.**

### Q23. SQLite for lyrics, prompts, history
**Locked: YES — SQLite added.** v3 dismissed SQLite as over-engineering for 1 album. **v3.1 reverses that.** Lyrics are inherently relational (track → many drafts → many lines), API prompts deserve a queryable history, quota snapshots are time-series, decisions and events are a log. JSON manifests get clunky for these.

**The shape:** ONE SQLite database at `.meta/sonic-studio.db`. 12 tables: `albums`, `tracks`, `lyrics_drafts`, `lyrics_lines`, `api_prompts`, `api_responses`, `events`, `decisions`, `quota_snapshots`, `cassette_stickers`, `intake_briefs`, `pipeline_state`. ~150 lines of DDL in `tools/sonic_studio/schema.sql`.

**The split:** SQLite is the build-skill's internal store (Python-only). The studio shell never queries SQLite directly — it reads JSON snapshots the build skill exports (`albums.json`, `state.json`, `events.jsonl`). The OneDrive mirror includes `.meta/sonic-studio.db` — that's the backup.

**Cost:** +400 lines (schema.sql + db.py helpers + new scan/invoke logic). +50ms per action (irrelevant). +1 dep, but `sqlite3` is stdlib (no pip install).

**Why one DB, not per-album:** queries cross albums ("every failed generation across all albums"). Per-album DBs would force federated queries.

### Q24. In-browser MP3 playback verification
**Locked: YES, verified.** Same-origin HTTP serves the HTML AND the MP3s from the project root. Chromium allows `<audio>` to read same-origin resources without Range headers, without streaming, without a daemon. MP3 files are 5–8 MB; whole-file load is ~50–100ms over localhost.

**Verified constraints (post-research, 2026-07-28):**
- `file://` + cross-folder `<audio src=file://...>` is BLOCKED by Chromium
- `http://localhost:8000` + same-origin MP3 is UNRESTRICTED
- No Range parsing needed
- Works in Chrome, Firefox, Edge, any modern browser
- Tested static server boot in this session (`python -m http.server`); port 8000 will be the default

**Day 2 sub-task added:** `scan.py` must copy MP3s from OneDrive canonical to `music/<slug>/music/` in the project on first scan. Otherwise Day 3 has no files to play.

### Q25. SQLite database location
**Locked: `.meta/sonic-studio.db`.** Co-located with other studio state (state.json, events.jsonl, build-skill.lock, pipeline-deps.json). The db is the most complete state (SQLite source of truth); JSON exports are derived from it.

**Why not `.db/` or `data/`:** no new folder needed, one rsync/cp for backup (`.meta/` is already mirrored as a unit), hidden-dir convention signals "metadata the agent owns, don't edit by hand." The OneDrive albums folder is canonical album content; the project's `.meta/` is the studio's working state — different concerns, different locations.

### Q26. SQLite WAL mode
**Locked: YES — WAL mode on, with `synchronous=NORMAL`.** Standard pairing for WAL. Applied via `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL; PRAGMA foreign_keys=ON; PRAGMA busy_timeout=5000;` on every connection open.

**Why WAL:** build skill is the only writer; readers (chat feed polling events.jsonl, library polling albums.json, dashboard polling state.json) shouldn't block during long generation writes. WAL gives multi-reader + 1-writer without blocking, faster reads and writes for our workload.

**The 3-file cost:** `.db` + `.db-wal` + `.db-shm`. All three live in `.meta/`. Mirror only `.db` to OneDrive; `.db-wal` and `.db-shm` are local-only runtime artifacts (rebuilt on next open if missing).

**Backup discipline:** `PRAGMA wal_checkpoint(TRUNCATE)` runs at the end of every scan/invoke before OneDrive mirror copies `.db`. TRUNCATE forces a clean checkpoint so the `.db` file is self-contained and safe to mirror.

## 3. The contract (the README gets amended)

The current README says:
> "Not a backend / API. Both pages are pure static HTML + inline CSS/JS."

This is **mostly still true**. The amendment is small:

> **v3.1 amendment:** The studio uses one auto-started local HTTP server (`python -m http.server 8000`) for **same-origin MP3 delivery** to the in-browser cassette player. The server is stateless, runs only while the user is actively using the studio, and is spawned by the build-skill entrypoint. It is not a daemon, not a service, not persistent across reboots.

The README also needs to add:

> **v3.1 amendment:** The studio is **independent of Hermes**. It has its own chat panel for build-skill feedback, its own pipeline buttons, and its own state. Switching albums starts a new chat session. Old chat sessions are archived to `events-archive.jsonl`.

## 10. The OneDrive mirror (Q16, locked)

Every file written by v3.1 build triggers a mirror:

```
Desktop (canonical during build): ~/Documents/Projects/sonic-studio/
OneDrive mirror: ~/OneDrive/Hermes/Agents/planning/sonic-studio/

Mirror loop (after each write):
  for f in <changed>; do
    o=<mirror>/$(basename $f)
    [ ! -f "$o" ] || [ $(stat -c%s "$f") != $(stat -c%s "$o") ] && cp "$f" "$o"
  done
  md5sum verify byte-match on the changed files
```

For album assets (the canonical files in OneDrive), the direction is reversed — the OneDrive folder IS canonical, the project gets a copy on build.
